# Feature Roadmap

Prioritized feature ideas for Eshu Gateway. This is a working document — each
feature has a spec, its open decisions (with a recommendation), and an effort
estimate. Build order is by priority; each feature ships with the standard
test → verify → merge to `master` → LXC pull flow.

## Priority order

| # | Feature | Why | Effort |
|---|---------|-----|--------|
| ~~P1a~~ | ~~Emergency Freeze~~ | **DONE** — shipped on `feat/emergency-freeze`, merged to master | Low |
| ~~P1b~~ | ~~Fleet Run (Ansible-lite)~~ | **DONE** — shipped on `feat/fleet-run` | Medium |
| ~~P2~~ | ~~"What could go wrong" Risk Hint~~ | **DONE** — shipped on `feat/risk-hint` (+ dry-run suggestions in Fleet Run) | Low |
| **P3** | Approver Keyboard Shortcuts | QoL win for a single operator triaging bursts | Low |

### Dropped / deferred

- **Natural Language Policy Editor** — dropped (low value for a single operator; grammar complexity not worth it).
- **Fleet health scorecard** — dropped (all gateways are usually healthy; per-gateway pills already exist).
- **Deferred ideas (future consideration):** per-agent identity & accountability, Telegram/phone approval, scheduled freeze, command timeline, time-to-approval stats, weekly activity digest, blocked-attempt alerting thresholds, cron/timer job visibility.

## Approved Windows decoupled from the feature system ✅ DONE

Shipped on `feat/windows-core`. Approved Windows are now **core / always-on** —
no longer a toggleable feature flag. `fetch_policy` always delivers the active
windows for a gateway (data-driven; the poller already syncs the
`approved_windows.sh` feature script based on data presence, not the flag). The
`approved_windows` row is removed from `feature_flags` (existing rows cleaned up
on startup), and the dev-installer/agent-docs URLs for dev-mode gateways no
longer depend on the flag (also fixing the silent dev-push coupling). The
feature-flag *system* and feature-script delivery remain for future features.

---

## Zero-Trust Gateways ✅ DONE

Shipped on `feat/zero-trust-gateways`. Every Eshu gateway is already protected
(JIT, blocklists, freeze, allowlists) — **Zero-Trust** is the strictest tier: a
gateway where **allowlisted commands no longer auto-run**. Everything routes to
JIT, so the operator personally approves/denies every single command (with the
P2 ⚠ risk-hint visible in the queue). Approved-window tokens still auto-run
(pre-approved by the operator); Fleet Run is unaffected; freeze + blocklists
still reject first.

- Per-gateway `zero_trust` flag (ALTER `gateways`) + toggle
  `POST /api/gateways/{ip}/zero-trust` (session + audit `zero_trust_enabled/disabled`).
- `fetch_policy` carries `zero_trust` (mirrors `trigger_freeze`); the poller
  writes `/etc/eshu-zero-trust` (1/empty, atomic tmp+mv like `/etc/eshu-freeze`).
- Gateway: the exact/regex allowlist auto-run stages are skipped when the marker
  is present, so allowlisted commands fall through to JIT.
- UI: 🔒 ZT badge + toggle in the unified Gateways table.
- Ships via the deploy pipeline (poller + gateway scripts are embedded in the
  installers, regenerated by `gen_installer.py`).

Naming note: chosen because all gateways are protected by default — this tier
means *no implicit trust* (nothing auto-runs without operator approval).

## UI consolidation ✅ DONE

The powerful features used to live in different places. Shipped on
`feat/controls-consolidation`. Operational controls are grouped under
**Controls**, preferences live in **Settings**, the record trail has its own
**Logs** view, and gateway lifecycle (cards + overrides + enrollment) lives in
one **Gateways** tab. Fleet Run stays its own top-level tab.

### Final navigation

| Tab | Contents |
|-----|----------|
| Dashboard | Main queue, gateway cards, live view. **Risk Hint renders here**, next to the command, before you Approve. |
| **Gateways** | Full-width **Gateway Enrollment** (SSH keys, one-liner) + a **unified gateway table** (Status · Gateway · IP · Enrolled · Policy · Health · Override · Uninstall). All gateway data points in one place. |
| Windows | Approved Windows (unchanged, stays its own top-level tab). |
| Statistics | Stats & **Policy Suggestions** (per-gateway, NEW badges, Allowlist/Dismiss, Mark All Seen) — the read-only Policy Gaps widget was removed as redundant. |
| **Controls** | **🛡️ Global Central Policy** (Tester + exact/regex allowlists + blocklist, Save & Push) — full-width. **Emergency Freeze** lives in the sidebar (a persistent pill above Gateway Health); Development & Deployment moved to Settings behind the dev-tools toggle. |
| Fleet Run | Queue + Dispatch + per-gateway results (unchanged, own tab). |
| **Settings** | Notifications · External Notifications (webhook) · Dashboard Password. |
| **Logs** | Audit Log + search. |

The sidebar groups these under **Navigation** (Dashboard · Gateways · Windows ·
Statistics) and **Operations** (Controls · Fleet Run), with Settings · Logs ·
Log Out at the bottom.

## P1a — Emergency Freeze ✅ DONE

### What

One button that makes **every gateway reject all commands** — including
whitelisted and window-token commands — until unfrozen. A circuit breaker for
the whole fleet.

Shipped on `feat/emergency-freeze` (merged). Adds the **Controls** tab with the
Emergency Freeze sub-section; Override Mode moved there too in the UI
consolidation pass.

### How

- Backend (`main.py` + `db/gateways.py`): global `trigger_freeze` meta key with
  `set_trigger_freeze()` / `clear_trigger_freeze()` / `get_trigger_freeze()`
  (mirrors the existing `trigger_uninstall` pattern).
  Endpoints: `POST /api/freeze`, `POST /api/unfreeze`, `GET /api/freeze/status` —
  all `_check_session`, audit-logged (`freeze_started` / `freeze_ended`).
- Policy payload: `policies['trigger_freeze']` in `fetch_policy`, next to `trigger_uninstall`.
- Poller (`eshu-poller.sh`): parse the flag, write `1`/empty to `/etc/eshu-freeze`
  atomically (tmp + mv, like the policy files).
- Gateway (`eshu-gateway.sh`): new stage 0 before the blocklist — if
  `/etc/eshu-freeze` contains `1`, reject with a clear "fleet is frozen" message.
- UI: a **sidebar Freeze pill** (above Gateway Health) that turns red/"Frozen" when
  active, plus a persistent banner (modeled on the override banner); poll
  `/api/freeze/status`.

### Open decisions

| Question | Recommendation | Status |
|----------|----------------|--------|
| Reject everything, incl. whitelisted/windows? | **Yes** — freeze is absolute. | ✅ Resolved — Stage 0 runs before the blocklist |
| ≤30s propagation (next poll cycle) acceptable? | **Yes** — surface "takes effect within 30s" in the UI. | ✅ Resolved — shown on the Freeze button + status label |
| Per-gateway freeze too? | Defer — global only for v1. | ✅ Deferred — global only |

## P1b — Fleet Run (Ansible-lite) ✅ DONE

Shipped on `feat/fleet-run` (not yet merged). Queue commands in the dedicated
**Fleet Run** tab, then hit **Dispatch** — one approval sends everything to the
selected gateways, with per-host results (printed output + exact run times).
**v1 is user-only** (agent-origin submissions deferred).

### How

```
Compose/Request ──▶ Fleet Run (pending)
       │
Approve (1 click, validated, audit-logged) ──▶ per-gateway result rows created
       │
Existing 30s policy poll injects pending_fleet_cmd + cmd_id
       ▼
Each selected gateway: poller runs via systemd-run (detached, survives restarts)
       ▼
Poller POSTs result back (running / success / failed + exit_code + output)
       ▼
Dashboard aggregates → per-gateway status + expandable output
```

- **Data model:**
  `fleet_commands(id, command, status[pending|approved|denied|complete],
   target_ips, origin[operator|agent], reason, created_at)`
  `fleet_results(id, cmd_id, gateway_ip, status[queued|running|success|failed|timeout],
   exit_code, output, started_at, finished_at, UNIQUE(cmd_id, gateway_ip))`
- **Endpoints:**
  - `POST /api/fleet/commands` — session or gateway-token (agent → pending)
  - `GET /api/fleet/commands` — session
  - `POST /api/fleet/commands/{id}/approve` — session (the single approval point)
  - `POST /api/fleet/commands/{id}/deny` — session
  - `POST /api/fleet/commands/{id}/result` — gateway-token
- **Delivery:** inject `pending_fleet_cmd` only into the selected gateways'
  `/api/policy/{ip}` responses. Poller tracks last-processed `cmd_id` for
  idempotency (same pattern as `LAST_TRIGGER_ID`).
- **Execution:** `systemd-run --unit=eshu-fleet-<id> --collect bash -c "cmd"`
  (same pattern as the uninstaller) so long commands don't block the poll loop.
- **Safety:**
  - Approval-time validation runs the command through the same policy test
    logic — **hardcoded catastrophic blocklist** (`rm -rf`, `mkfs`, `dd`,
    `iptables`, `reboot`, …) → **hard-reject at the dashboard**; regex-blacklist
    matches → warn with override.
  - `timeout` wrapper (default 180s, per-command override).
  - Refuses to dispatch while the fleet is frozen.
  - Output truncated (1MB cap; list shows a preview, full output fetched on demand) per result.
- **UI:** Fleet Run sub-section in the Controls tab — compose box (command +
  target gateways via checkboxes + timeout + reason), pending approvals,
  per-gateway result rows with expandable output.

### Open decisions

| Question | Recommendation | Status |
|----------|----------------|--------|
| Target selection | **Subset from v1** (All / checkbox selection). | ✅ Resolved |
| Default timeout | **180s**, per-command override (1–3600). | ✅ Resolved |
| Blocklist-hit commands | **Hard-reject catastrophic set**; warn (with override) for regex-blacklist matches. | ✅ Resolved |
| UI location | **Dedicated Fleet Run tab**; per-gateway results print output + exact run times. | ✅ Resolved — changed during build |
| Approval | **Queue + Dispatch**: add commands to a slim queue, one **Dispatch** button sends them all (that is the approve). No separate approval section. | ✅ Resolved — changed during build |
| Agent submissions | Always **pending** — operator is the gate. | ⏸ **Deferred** — v1 is user-only; agent-origin fleet may come later (AI already has approved windows) |
| Reason | Optional for operator-origin. | ✅ Resolved — optional |
| Privilege | Runs as **root** via systemd-run (same as gateway scripts). | ✅ Resolved |

## P2 — "What could go wrong" Risk Hint ✅ DONE

Shipped on `feat/risk-hint` (not yet merged). Static, word-boundary-aware rule
map (`core/cmd_risk.py`) surfaces a one-line amber ⚠ risk hint — in the main
queue for **pending** JIT rows (tooltip) and in the Fleet Run dispatch queue
when a command is added. Also ships **dry-run suggestions**: when a known-safe
dry-run variant exists (`apt-get install`, `npm install`, `pip install`), the
Fleet Run queue shows a 💡 suggestion with a **Use** button, and the Dispatch
confirmation warns when queued commands have a dry-run upgrade available.

### How

- New static map `dashboard/core/cmd_risk.py` with
  `get_cmd_risk(cmd) -> str | None` (word-boundary regex rules):
  - `systemctl restart/stop` → "Restarts/stops a service — brief outage"
  - `docker rm` / `docker rmi` → "Removes containers/images — data loss"
  - `journalctl --vacuum` / `truncate` → "Rotates/truncates logs"
  - `pip`/`npm`/`apt(-get)`/`dnf`/`yarn` install → "Installs packages — modifies the system"
  - `\brm\b` → "Deletes files — irreversible"; plus `kill -9`, `chmod 777`,
    `userdel`, `find / … -delete`
- Plus `get_dry_run_suggestion(cmd) -> str | None` for verified dry-run flags.
- Backend: `/api/requests` adds `risk` (pending-only); `/api/policies/test`
  returns `risk` + `dry_run`.

### Open decisions

| Question | Recommendation | Status |
|----------|----------------|--------|
| Where rendered | **Main queue, beside the command** + Fleet Run queue. | ✅ Resolved |
| Show on historical rows too? | Pending + approve action only; keep history clean. | ✅ Resolved |
| Source | Static curated map — no model. | ✅ Resolved |
| Dry-run suggestions | Curated conservative map; opt-in "Use" button; Dispatch warns when available. | ✅ Resolved |

## P3 — Approver Keyboard Shortcuts

### What

While a JIT request is pending, keyboard shortcuts act on the **first pending
row** without needing to click buttons.

### How

- Global `document.addEventListener('keydown', ...)` in `app.js`.
- Keys: `A` approve · `D` deny · `J` jump/scroll to first pending · `N`/`P`
  next/prev pending · `Esc` dismiss dialogs/banners.
- Guard: skip when the user is typing in an input/textarea (`e.target.tagName`),
  and only active when a request is actually pending.
- Action reuses the existing `handleAction(id, 'approve'|'deny')`.
- Floating hint chip ("A=Approve · D=Deny · J=Next") shown only while pending > 0.

### Open decisions

| Question | Recommendation |
|----------|----------------|
| Key set | `A D J N P Esc`. |
| Active scope | Global, but input-guarded. |

## Build order & workflow

Each feature is a separate session with the standard flow:

1. Implement (backend → poller/gateway → UI → tests)
2. `bash scripts/pre-commit.sh` + `python3 -m pytest tests/`
3. Commit to `feat/override-mode`, push, fast-forward merge to `master`, push
4. LXC: `git pull` + restart; deploy via Seed Edge → Push to Dev → verify →
   Deploy to Fleet where the change touches gateway scripts
5. Update this roadmap (mark done) and the CHANGELOG

Order: **Freeze → Fleet Run → Risk Hint → Keyboard**.
